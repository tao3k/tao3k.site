** 1. Context and Problem Statement

=tao3k.site= starts as an empty project. Its first product surface will be a
commercial website for
[[https://github.com/tao3k/xiuxian-artisan-workshop][=tao3k/xiuxian-artisan-workshop=]].

The site must speak to three audiences without collapsing into a generic AI SaaS
landing page:

1. prospective customers who need local, private, cloud, API, and model
   deployment options;
2. VC or strategic partners who need category clarity, business lifecycle, and
   technical moat;
3. developers who need a credible path into the open-source Rust-first
   monorepo, docs, APIs, and package boundaries.

The design must reflect the real =xiuxian-artisan-workshop= identity:

- Rust-owned contracts, runtime, routing, verification, and persistence;
- Wendao for knowledge/search/gateway and computable graph surfaces;
- Qianji for workflow/control-plane execution;
- Qianhuan for context/persona rendering;
- Daochang for native agent-loop hosting;
- Apache Arrow and Arrow Flight as the high-performance data/transport plane;
- Julia compute bridge for high-performance analytical and engineering
  workflows;
- high-performance HTTP, gRPC, and Arrow Flight APIs for external service
  integration.

** 2. Decision

Build a multi-page commercial site using the following stack:

- *TanStack Start* for the full-stack React shell, type-safe routing, route
  data boundaries, and future server functions.
- *Effect* as the TypeScript domain layer for typed content registries,
  lifecycle models, simulated runtime traces, feature flags, and failure-aware
  data loading.
- *React Aria* for accessible navigation, tabs, buttons, disclosures, dialogs,
  menus, and keyboard interaction contracts.
- *Lightning CSS* for modern CSS parsing/transforms, design tokens,
  responsive layout, and motion styling.

The first implementation must be a *runtime-surface commercial site*, not a
static brochure. It should present =xiuxian-artisan-workshop= as a living
agent-infrastructure lifecycle:

1. *Native agent infrastructure*: Rust runtime, native tool routing, service
   contracts, security, storage, and model/provider seams.
2. *Knowledge-to-workflow lifecycle*: Wendao grounds and ranks context;
   Qianji turns that context into controlled workflows.
3. *Verified AI operations*: Qianhuan and Daochang shape context and host
   auditable agent work.
4. *High-performance compute and transport plane*: Apache Arrow, Arrow
   Flight, and Julia provide a columnar, cross-language computation path for
   engineering intelligence.

** 3. Route Contract

The first route set is:

| Route | Purpose |
|---+---|
| =/= | Commercial homepage with an animated lifecycle/runtime surface. |
| =/platform= | Platform architecture: Wendao, Qianji, Qianhuan, Daochang, Julia compute, and Apache Arrow/Flight data plane. |
| =/api= | API and integration surface for Wendao/Qianji HTTP, gRPC, and Arrow Flight services. |
| =/deployment= | Local-first, private/on-prem, cloud, hybrid, and model deployment solutions. |
| =/enterprise= | Customer and VC narrative: governance, auditability, deployment trust, and business value. |
| =/open-source= | Developer entrance: GitHub, Rust-first monorepo, package groups, docs/RFCs, and CLI surfaces. |
| =/research= | Technical moat: computable graph, typed relations, graph ranking, Arrow/Flight, workflow control, and verified traces. |

The misspelled =/depoyment= path should redirect to =/deployment= so early
handwritten links do not break.

The primary navigation is:

=Platform / API / Deployment / Enterprise / Open Source / Research / GitHub=

** 4. Page Decisions

*** 4.1 Homepage

The homepage first viewport should show a dynamic runtime surface:

- left side: category claim and lifecycle summary;
- right side: animated computable graph plus terminal-style runtime trace;
- below: lifecycle phases for agent infrastructure, knowledge-to-workflow,
  verified operations, and compute/transport plane;
- proof band: Rust-owned contracts, computable graph, Arrow Flight transport,
  Julia compute bridge, verified workflow control.

The page must avoid generic AI SaaS gradients and vague automation claims. It
should feel like a technical workshop surface: dark, precise, traceable, and
alive.

*** 4.2 Platform

The platform page owns the interactive lifecycle explorer:

- *Wendao*: knowledge/search/gateway, computable graph, retrieval plans,
  repo intelligence, Arrow/Flight query surfaces.
- *Qianji*: workflow/control plane, Flowhub, BPMN control, checkpoints, human
  task states, runtime advancement.
- *Qianhuan*: context/persona rendering, template binding, prompt/context
  contracts.
- *Daochang*: native agent loop, host runtime, native tool execution, runtime
  integration.
- *Julia Compute Bridge*: high-performance analytical kernels, engineering
  computation, model/simulation-adjacent analysis.
- *Apache Arrow + Arrow Flight*: columnar contracts and service transport
  connecting Rust runtime, Python adapters, Julia computation, and enterprise
  consumers.

*** 4.3 API

The API page is a first-class product surface, not a documentation afterthought:

- Wendao HTTP/gRPC/Arrow Flight APIs for search, gateway, repo intelligence,
  and high-throughput structured data access.
- Qianji HTTP/gRPC APIs for workflow start, state advancement, checkpointing,
  human-task coordination, BPMN/Flowhub control, and execution trace access.
- Transport positioning:
  - HTTP for broad integration;
  - gRPC for service-to-service invocation;
  - Arrow Flight for columnar, high-throughput data exchange.
- Proof surfaces should include typed contracts, topology diagrams, request and
  response examples, and lifecycle traces.

*** 4.4 Deployment

The deployment page answers how customers can run the system:

- local workstation and lab deployments;
- private/on-prem deployments for internal knowledge and compliance-sensitive
  workflows;
- cloud deployments for hosted gateways, runtime services, and storage/data
  planes;
- hybrid deployments where private knowledge remains local while selected
  services run in cloud infrastructure;
- model deployment options for local models, cloud models, OpenAI-compatible
  endpoints, and future multi-provider routing;
- operations posture: observability, validation gates, audit traces, workflow
  checkpointing, and deployment-specific runtime settings.

*** 4.5 Enterprise

The enterprise page should frame the business value:

- turn knowledge repositories into controlled agent workflows;
- reduce brittle LLM JSON glue by using typed contracts and native service
  surfaces;
- preserve auditability across retrieval, workflow, context rendering, and
  operation execution;
- support engineering intelligence and computational workflows through Arrow
  transport and Julia computation.

*** 4.6 Open Source

The open-source page should preserve the hacker/developer entrance:

- GitHub repository link;
- Rust-first monorepo positioning;
- primary package groups;
- docs/RFC entry points;
- CLI/API surfaces;
- validation culture.

*** 4.7 Research

The research page should explain the moat:

- why passive vaults are insufficient for agent systems;
- why computable graphs, typed relations, graph ranking, and vector/search
  fusion matter;
- why columnar data contracts matter for agent infrastructure;
- why workflow control and verified traces are central to safe operations;
- why Rust owns contracts/runtime while Julia owns high-performance
  computation.

** 5. Domain Model

The site content should be expressed through Effect-managed typed registries,
not scattered page-local constants.

Core models:

- =LifecycleStage=: native agent infrastructure, knowledge-to-workflow,
  verified operations, compute/transport plane.
- =PlatformModule=: Wendao, Qianji, Qianhuan, Daochang, Julia Compute Bridge,
  Apache Arrow/Flight Data Plane.
- =ApiSurface=: Wendao HTTP, Wendao gRPC, Wendao Arrow Flight, Qianji HTTP,
  Qianji gRPC, future service surfaces.
- =DeploymentMode=: local, private/on-prem, cloud, hybrid, model deployment.
- =RuntimeTrace=: homepage and platform demo traces. First version is a
  deterministic front-end simulation based on static product data, not a claim
  of live production telemetry.
- =ProofPoint=: concise evidence-oriented claims for customers and VC.

** 6. Accessibility and Interaction Contract

React Aria is the default for interactive controls. Required behaviors:

- keyboard-reachable global navigation and route menus;
- skip link to main content;
- accessible tabs for platform/API/deployment explorers;
- visible focus states;
- reduced-motion handling for runtime animations;
- semantic headings and landmarks;
- button/link distinction preserved for command vs navigation actions.

** 7. Visual System

The site visual language should be:

- dark technical workshop, not generic AI SaaS;
- precise lifecycle diagrams and trace surfaces, not decorative fantasy;
- restrained palette with neutral dark base plus green, blue, amber, and rust
  accents;
- animated graph/trace/lifecycle states where motion communicates system
  behavior;
- high-density enough to feel technical, but readable for customers and VC.

** 8. Alternatives Considered

- *Static investor deck website*: strongest for simple VC readability, but too
  weak for the =xiuxian-artisan-workshop= runtime identity.
- *Interactive lab first*: strongest "fancy hacking" signal, but too much
  implementation weight before the commercial and deployment story is clear.
- *Developer docs-first site*: easiest to derive from the repository, but it
  would under-serve customers and VC and collapse back into a README surface.

** 9. Consequences

*** Positive

- The website becomes a product surface that demonstrates lifecycle thinking,
  API/deployment readiness, and high-performance compute/data-plane posture.
- The stack mirrors the product values: typed routing, functional domain
  modeling, accessible interactions, and fast CSS transformation.
- The route structure separates customer, VC, developer, API, deployment, and
  research narratives without fragmenting the core lifecycle.

*** Negative / Trade-offs

- The runtime-surface design costs more than a static landing page.
- The first dynamic traces must be carefully labeled and implemented as
  deterministic product demos until real service telemetry is connected.
- The site requires a typed content model early, which adds initial structure
  before there is much page volume.

** 10. Implementation Plan

1. Scaffold TanStack Start, TypeScript, React, React Aria, Effect, and Lightning
   CSS inside =tao3k.site=.
2. Add route tree for =/=, =/platform=, =/api=, =/deployment=, =/enterprise=,
   =/open-source=, and =/research=, plus =/depoyment= redirect.
3. Define design tokens, global layout, navigation, footer, and reduced-motion
   behavior.
4. Implement Effect-backed content registries for lifecycle, platform modules,
   API surfaces, deployment modes, proof points, and deterministic traces.
5. Build the homepage runtime surface and lifecycle proof band.
6. Build platform, API, deployment, enterprise, open-source, and research route
   skeletons with complete first-pass content.
7. Add accessibility checks, route smoke tests, typecheck, lint, and production
   build verification.
