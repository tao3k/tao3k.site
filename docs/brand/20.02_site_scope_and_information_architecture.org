* Purpose

This record defines the maintenance boundary and information architecture of tao3k.site, the umbrella website for the complete tao3k ecosystem.

The site communicates the tao3k vision, long-term direction, values, ecosystem structure, and open-source entry points. It is not a replacement documentation portal for every project.

* Main-site ownership

tao3k.site owns:

- the tao3k brand doctrine, vision, and mission;
- the company and ecosystem overview, commercialization boundary, and long-term stewardship;
- the Evidence-to-Action lifecycle narrative;
- the ecosystem and product-role map;
- the main-site Roadmap;
- Human Agency, Technical Equity, and other shared principles;
- Open Source First, community value, customer rights, portability, and the public-to-commercial value loop;
- Research-to-Operations positioning;
- the Comparison narrative and editorial policy;
- the open-source Products directory and external links;
- clear exits from macro site claims to the responsible project GitHub repositories and Docs;
- the independent tao3k.site theme, content, accessibility, Mobile behavior, performance, deployment, and site contracts; and
- the information architecture and content contracts required to maintain the site.

* Out of scope

tao3k.site does not own:

- detailed APIs, implementation status, tests, benchmarks, or support matrices for another project;
- another project's internal architecture, release notes, issue plan, or engineering Roadmap;
- duplicated project documentation that can become stale independently;
- capability claims that are not supported by the responsible project's documentation; or
- a central implementation truth matrix for the entire ecosystem.

The main site may describe a project's role in the tao3k ecosystem. The responsible project remains authoritative for implementation facts.

* Documentation authority

Every Products entry links to the responsible GitHub repository and project documentation. If the main site summarizes current capability or maturity, that statement must be sourced from the project-owned documentation rather than maintained as an independent fact.

Platform and architecture records in tao3k.site define brand-level roles, relationships, future direction, and site narrative. They do not supersede project-owned technical documentation.

** Platform, Products, and Solutions taxonomy

The three destinations describe different public object types. They are not
three editorial variations of the same capability list.

| Destination | Canonical object | Question answered | Owns | Must not own |
|-
| Platform | Shared capability domain and system law | How does the tao3k system work across products and industries? | architecture, contracts, lifecycle, authority, data, compute, operations, deployment | project catalogues, vertical sales stories, duplicated release status |
| Products | Independently adoptable and maintained deliverable | What can a user install, integrate, extend, or procure? | identity, role, owner, repository, docs, release and adoption boundary | ecosystem-wide architecture, invented implementation facts, industry outcome claims |
| Solutions | Outcome-specific system composition | How is a concrete industrial or research problem addressed? | problem, accountable user, composition, workflow, deployment profile, evidence and authority boundary, expected outcome | generic feature catalogues, disguised product directories, terminal vertical SaaS claims |

*** Classification tests

1. If the concept survives replacement of every current implementation, it is
   Platform.
2. If it has an independent identity, owner, repository or distribution unit,
   documentation, version or release lifecycle, it is a Product.
3. If it requires a named industry context, accountable actor, workflow,
   constraints, deployment setting, and outcome, it is a Solution.
4. If an item passes more than one test, one canonical owner is selected and the
   other pages reference it instead of copying its explanation.

*** Shared facets

Deployment locality, lifecycle stage, maturity, audience, evidence grade, and
authority risk are facets, not primary navigation categories. The same Platform
capability, Product, or Solution may be filtered or annotated by these facets
without changing object identity.

*** Reference direction

Platform defines each shared capability once. Products declare which Platform
capabilities they implement or expose. Solutions compose Platform capability
references, Product references, customer or partner components, and a deployment
profile. Project-owned documentation remains authoritative for shipped status,
APIs, benchmarks, and release evidence.

*** Platform content boundary

Platform is the customer-facing system of stable responsibilities connecting
evidence, knowledge and data, reasoning and science, qualification, governed
operation, and reproducible delivery.  It answers how an enterprise constructs
and operates a qualified vertical AI system.  It does not answer which project
owns a repository, which industry scenario should be adopted, which competitor
is preferable, or why tao3k holds a social principle.

The overview and subroute contract is defined in
[[file:../platform/10.07_platform_information_architecture.org][Platform Information Architecture]].
Platform capability pages reference Products as implementation evidence and
Solutions as applied compositions.  They must not copy either destination's
canonical content.

* Primary navigation

The primary Navigator is:

| Item | Destination | Responsibility |
|-
| Logo | =/= | Return to the tao3k home page |
| Vision | =/vision= | Why tao3k exists and what future it seeks |
| Platform | =/platform= | The Evidence-to-Action lifecycle and ecosystem foundations |
| Products | =/products= | Open-source directory with GitHub and Documentation links |
| Roadmap | =/roadmap= | The long-term tao3k ecosystem direction |
| Principles | =/principles= | Values, Human Agency, Technical Equity, and responsibility |
| Compare | =/compare= | Category boundaries and evidence-backed comparison |

GitHub and Documentation may appear as distinct utility actions on the right side of the desktop Navigator and inside the Mobile menu.

* Audience proof lenses

The main site presents one ecosystem and one body of truth. Enterprises, research institutions, communities, and long-term partners enter through different proof obligations, but the site must not create four incompatible product stories or audience-specific capability claims.

- Enterprise lens :: accountable operation, qualification, authority, recovery, integration, and exit;
- Research lens :: reproducibility, assumption and limit preservation, field evidence, and revision;
- Community lens :: inspectability, learning, self-hosting, extension, contestability, attribution, and meaningful exit;
- Long-term partner lens :: durable value through evidence, operational responsibility, standards, expertise, and non-extractive ecosystem growth.

Audience lenses change which proof question is foregrounded, not which underlying facts, maturity labels, or project boundaries apply.

* Canonical navigation architecture

The primary navigation answers stable public questions rather than mirroring repositories, internal teams, or audience segments.

- Home =/= :: Why does tao3k need to exist? The eight-section homepage narrative remains owned by [[file:20.03_homepage_content_contract.org][Homepage Content Contract]].
- Ecosystem =/ecosystem= :: How does the Evidence--Action Ecosystem work? This is the public label for the lifecycle, four layers, and shared contracts; /Platform/ is not the primary navigation label.
- Research to Operations =/research-to-operations= :: How does research become governed operation and return as evidence?
- Open Source =/open-source= :: What can a visitor inspect, use, and contribute to today? This is the public navigation label for the role-grouped project directory; /Products/ remains an internal information-architecture term where needed.
- Comparison =/comparison= :: How is tao3k different from systems people already know? Framework, maintained products, and Evidence Watch remain distinct evidence surfaces.
- Roadmap =/roadmap= :: What is available, under construction, under research, and a long-term horizon?
- Company =/company= :: What kind of institution is tao3k trying to become, how is commercial value sustained, and what responsibilities remain public?

Utility actions are =/docs=, the tao3k GitHub organization, and =/work-with-us=. They must not replace the public position or fragment the main narrative.

=/docs= is a directory of responsible Project Docs, not a public rendering of internal brand and company specifications. =/work-with-us= first distinguishes enterprise integration, research partnership, open-source collaboration, institutional or standards partnership, and long-term strategic or investment relationships before collecting relationship-specific information.

Desktop and mobile presentation may group or collapse these entries, but the labels, route responsibilities, and single-truth boundary remain stable. No audience receives a separate capability truth.

* Route responsibilities

** Home

The home page presents the complete brand narrative: doctrine, problem, lifecycle, ecosystem, Research-to-Operations mission, Roadmap preview, values, and open-development entry points.

** Vision

Vision owns the future world tao3k seeks, the long-term mission, the relationship between intelligence and legitimate action, and the commitment to human value.

** Platform

Platform explains the shared lifecycle and how knowledge, records, graph intelligence, scientific computation, qualification, Agent systems, verification, and evolution connect. It does not reproduce each project's technical manual.

** Products

Products is an external open-source directory. It explains each project's ecosystem role and provides GitHub and Documentation destinations.

** Roadmap

Roadmap describes long-term tao3k development directions, current construction fronts, and research horizons. It does not aggregate repository issues.

** Principles

Principles expresses the non-negotiable values that shape product and technical decisions.

** Compare

Compare explains why tao3k differs from Agent platforms, workflow engines, knowledge graphs, retrieval systems, tracing tools, and conventional Agent cores. Named product comparisons require current evidence.

* Research to Operations

Research-to-Operations is a core mission presented prominently on Home, Vision, and Platform. It may have a dedicated route, but it does not need another permanent top-level Navigator item if that would reduce clarity on smaller screens.

* Products Navigator behavior

Products opens a desktop menu containing a limited, scannable list of open-source projects, their short roles, and direct GitHub and Documentation actions. A =View all products= action enters =/products=.

The menu does not contain detailed feature matrices or long descriptions. Those belong to the project documentation.

* Page implementation boundary

The application page registry is a routing boundary, not a page implementation
module.  =theme/src/site-pages.tsx= maps stable route IDs to independently owned
page components and supplies the shared document shell.  It must not accumulate
page copy, datasets, timers, visual state machines, or page-owned CSS.

Each primary route owns a directory under =theme/src/pages/=.  Its TypeScript
and CSS remain colocated.  A complex interactive feature becomes a child module
inside that route directory when it owns state, animation, accessibility
behavior, or a distinct visual contract.  The Platform delivery model therefore
owns its Scheme-to-SDLC-to-SDOS state machine and styles separately from the
Platform overview and deployment-mode pages.

=site-pages.css= is restricted to the small cross-route shell and responsive
coordination layer.  Page-owned selectors belong to their page module.  Moving
code out of the registry without separating ownership is not sufficient: the
dependency direction must remain registry -> page -> feature, never feature ->
registry.

* Mobile and accessibility

- The Navigator must not require hover.
- Products must open by explicit button activation and expose its expanded state.
- All menu items must be keyboard reachable and screen-reader labelled.
- Escape closes the current menu before leaving the page context.
- Focus returns to the control that opened the menu.
- External GitHub and Documentation links disclose that they leave tao3k.site.
- The Mobile menu presents the same information architecture without hiding Vision, Roadmap, or Principles behind product content.

* Editorial rule

The main site may state vision and future direction clearly, provided the language distinguishes aspiration from current implementation. Project facts remain linked, scoped, and project-owned.
