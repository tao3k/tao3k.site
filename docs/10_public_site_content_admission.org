* Purpose

The Tao3k public site is an overview for customers, prospective customers,
investors, and developers.  It explains system boundaries, customer value,
technical direction, and evidence of seriousness.  It is not a replacement for
package READMEs, RFCs, benchmarks, deployment runbooks, or implementation docs.

The public site and project documentation are separate editorial products:

| Surface | Owns | Does not own |
|---------+------+--------------|
| tao3k public site | company thesis, market problem, Platform architecture, Product experience, Solution outcomes, differentiation, selected engineering evidence, commercial path, and routes to inspect or engage | package APIs, language syntax, module inventories, theorem listings, build commands, benchmark internals, runbooks, and exhaustive repository status |
| project documentation | implementation contracts, APIs, source ownership, language and module semantics, proofs, tests, benchmarks, operations, contribution, and exact maturity evidence | company-wide positioning, duplicated sales narrative, or an independent version of the public site |

A project detail reaches the public site only after it is transformed into a
customer-, investor-, or developer-relevant claim.  The public site answers
=why this architecture matters= and =why tao3k can build it=, then links to the
owning project for =how it works exactly=.

Tao3k is an early-stage company building To-B AI infrastructure and systems.
The site makes the company thesis, technical foundations, product directions,
execution evidence, and path to commercialization understandable to investors,
prospective enterprise customers, and developers.  The company's stage explains
why the site presents an evidence-backed direction rather than a mature product
catalogue; it does not define startups as the customer category.

No repository is presented as a customer Product merely because it is public or
technically important.  Public site claims must be owned by a real repository
and supported by its source, canonical documentation, or repeatable evidence.

* Content admission rule

Every public statement must identify:

- owner :: the repository and responsible package or document.
- maturity :: current implementation, measured result, design direction, or
  future roadmap.
- evidence :: a source-backed capability, a released interface, a benchmark
  receipt, a scenario gate, or an explicit deployment definition.
- audience :: why the statement matters to a customer, investor, or developer.

The site must not turn an architecture ambition into a capability claim.  Exact
file coverage, throughput, retrieval quality, model-quality impact, deployment
atomicity, and rollback guarantees require current measured or executable
evidence before they appear as quantified public claims.

* Current source-backed classification

** Product: [[https://github.com/tao3k/xiuxian-artisan-workshop][tao3k/xiuxian-artisan-workshop]]

This is the current integrated product direction and technical prototype.  Its
repository describes a Rust-first native agent infrastructure that combines:

- =Wendao= :: knowledge and retrieval, including shared contracts, host/runtime
  behavior, Arrow Flight transport, bounded SQL helpers, and Julia/Modelica
  repository intelligence.
- =Qianji= :: workflow, Flowhub, BPMN control, validation, and runtime activity
  adapters.
- =Qianhuan= :: context and persona rendering.
- =Zhenfa= :: native tool and routing substrate.

The public Product page may say that these surfaces work together to explore a
future product system for knowledge, retrieval, workflow control, context, and
native routing.  It must link to the repository, state its current maturity,
and avoid presenting technical deployability as commercial availability.

The repository also has explicit retrieval-performance and quality-gate tooling:
p95/average latency gates, fixed query-matrix Top1/Top3/Top10 evaluation, and a
multi-run rollout sign-off.  The public site may describe the existence of
quality gates.  It must not advertise a current latency, corpus capacity, or
retrieval score until the associated current benchmark receipt is selected.

** Platform foundation: [[https://github.com/tao3k/orgize][tao3k/orgize]]

=orgize= is a Rust library, not a peer customer Product.  It parses Org into
non-mutating, source-backed data projections: source blocks, links, agenda
metadata, capture plans, publishing graphs, and runtime-adjacent Org features.
It belongs in the Platform knowledge/evidence story and may be named as an open
foundation behind stable references, Contracts, and durable human-readable
records.

** Platform foundation: [[https://github.com/tao3k/poo-flow][tao3k/poo-flow]]

=poo-flow= is a Gerbil Scheme Control Plane for higher-order strategies.  It
expresses policies, profiles, modules, workflows, sessions, and loop descriptors
as inspectable values before projecting them to execution backends.  It belongs
under Platform / Control Plane, not as a workflow-runtime product claim.

At the public system level, tao3k's dual-engine architecture is POO Flow plus
Cedar.  POO Flow is the compositional policy and control engine; Cedar is the
authorization engine.  They retain different responsibilities while sharing an
admitted authority and evidence boundary.

RFC 45-114 defines a nested proof boundary inside the Cedar side: the Cedar
Lean definitional engine and Cedar Rust production engine provide independent
semantic and executable observations.  This internal pair strengthens the
Cedar authorization engine; it does not redefine the public POO Flow + Cedar
dual-engine architecture.  Scheme/POO owns the native adapter,
capability-to-risk projection, arbitration policy, external-authority result,
and evidence projection.  Marlin remains the independent runtime execution
boundary.

The public Platform argument may state:

- POO Flow composes the policy, Profile, capability, authority-risk, and
  operational control context in which Cedar authorization is evaluated;
- Cedar provides the authorization decision while preserving its exact policy
  evidence;
- inside the Cedar proof boundary, the definitional and production engines
  consume one canonical policy-input identity;
- comparison covers the complete outcome---decision, determining policies,
  erroring policies, semantic version, and canonical input identity---rather
  than comparing only =Allow= or =Deny=;
- elevated authority requires strict per-request Lean/Rust lockstep;
- explicitly admitted ordinary authority may use the Rust hot path with pinned
  differential-randomized-testing evidence and bounded Lean shadow; and
- missing engines, completed disagreement, malformed projection, or ambiguous
  risk fail closed and retain a truthful receipt.

This is an architecture and engineering-evidence claim, not a completed product
availability claim.  The risk-tier arbitration direction and local Lean proof
owners exist; the concrete production adapter, pinned DRT execution, production
interoperability, and external empirical qualification remain open.

Industry context may be used without borrowing maturity.  Amazon Verified
Permissions is an AWS managed authorization service using Cedar, and
Microsoft's open-source Agent Governance Toolkit specifies an optional bundled
Cedar dispatcher.  These are evidence that Cedar is gaining production and
production-oriented recognition in the emerging Agent era; they are not tao3k
customer endorsements or evidence that POO Flow's production adapter is already
admitted.

** Platform foundation: [[https://github.com/tao3k/marlin-agent-core][tao3k/marlin-agent-core]]

=marlin-agent-core= explicitly states that it is not a terminal-user product
shell.  It is a typed, Org-native agent-runtime substrate for graph loops,
queries, policy integration, sandbox visibility, receipts, and replay.  The
public site may identify it as an open runtime foundation; it must not present
it as a standalone customer Product without a product layer above it.

** Platform foundation: [[https://github.com/tao3k/agent-semantic-protocols][tao3k/agent-semantic-protocols]]

=agent-semantic-protocols= owns shared protocol contracts, Hook runtime,

story, not in a customer Product catalogue.

For the POO Flow + Cedar dual-engine architecture, the public consequence is

and Cedar authorization.  Progressive disclosure may then reveal the nested

* POO Flow, Lean, and Cedar terminology

The public dual-engine architecture is *POO Flow + Cedar*, but the two engines
must not be presented as duplicate policy evaluators.

- Gerbil/POO is the higher-order control plane. It constructs and evolves the
  Agent system, composes roles and profiles, coordinates delegation, and derives
  constraints for different execution paths from one policy source.
- Cedar is the deterministic authorization microkernel at the effect boundary.
  It decides whether one concrete principal may perform one action on one
  resource in the supplied context.
- Lean is an independent proof direction for cross-step, cross-Agent, and
  lifecycle invariants, including declared workflow structure, traces, and
  receipts.
- The Agent runtime owns execution and persistence.

The main site may call POO Flow and Cedar the dual engine. It must describe Lean
as formal assurance over the composed system, not as a second Cedar engine or as
an interchangeable authorization implementation.
